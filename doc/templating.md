# Templating in html.lua

`html.lua` builds CSS/markup as literal string fragments -- no external template engine, per `doc/why-luam.md`'s "one language" reasoning (Lua itself, building strings with `table.concat`/`..`, already does loops/conditionals; a template language doesn't need to). Two small first-party mechanisms exist for the parts that recur often enough to be worth naming, and this doc is the convention for using them, not a proposal to replace either.

## `{{ }}` vs `{{{ }}}` (`render.lua`)

`render.render(template_str, ctx)` does `{{ expr }}` (HTML-escaped) / `{{{ expr }}}` (raw) interpolation against a context table, with dotted-path lookup (`{{{ layout.gutter }}}` reads `ctx.layout.gutter`). No loops or conditionals -- that's deliberate, see its own header.

- Use `{{ }}` for anything that could contain user-authored text ending up in HTML content -- it's the auto-escape that makes "forgot to call `html.html_escape`" impossible by construction instead of convention-dependent.
- Use `{{{ }}}` for trusted, code-controlled values that are never user text -- numeric layout constants, CSS/markup fragments you're deliberately composing raw. HTML-escaping a pixel count is harmless but pointless; HTML-escaping an already-rendered partial (see below) would double-escape it, which is why composition uses `{{{ }}}` deliberately, not `{{ }}` by default.
- **Migrating a `string.format`-built block**: any literal `%%` that existed only to survive `string.format`'s own escaping (e.g. `calc(100%% - ...)`) must become a single `%` once the block moves to `render.render` -- `string.gsub`-based interpolation has no `%%` escaping convention of its own. Check this in both the CSS itself and any `/* ... */` comment text inside the same string -- a comment sitting inside a converted block goes through `render.render` too.

## Shared layout tokens (`PLATFORM_LAYOUT`)

Numeric constants used by more than one CSS-building function (nav width, gutter, ...) live in one table, `PLATFORM_LAYOUT`, passed as `render.render`'s context (`{layout = PLATFORM_LAYOUT}`) rather than threaded as positional `string.format` arguments. The bug class this replaces: a shared value threaded into a multi-argument `string.format` call by *position* is one transposition away from silently rendering the wrong number, with no error -- named placeholders make that mistake structurally harder (each one says which value it wants) instead of relying on a human counting argument order correctly. A derived value used verbatim in the template (e.g. `gutter_x2 = PLATFORM_GUTTER * 2`) should be precomputed as its own field on the context table, not written as repeated arithmetic in the template string, so migrating a block stays an exact, verifiable byte-for-byte refactor of its rendered output.

**Ordering gotcha, real and already hit once:** `PLATFORM_LAYOUT` (and the raw constants it reads) must be defined *before*, textually, every function that closes over it. Luam's implicit-local assignment (`x = ...` at chunk scope, no `local` keyword needed) still follows real Lua scoping: a local's scope begins strictly after its own declaration. A function defined earlier in the same file that references a name assigned later doesn't see a forward reference to that later local -- it silently resolves to an unset global instead, so the table it builds looks fine at a glance but its fields are `nil`, and the failure only surfaces at render time (`render: "layout.gutter" not found in context`), not at parse/build time. Define constants and any table built from them in one place, before the functions that use them, not interleaved.

## Composing partials

Render an inner fragment to a string first, then embed the *result* into an outer template as a raw `{{{ }}}` value -- this already works with no changes needed, it's just a convention worth naming: it's how a "layout" and the pieces inside it stay two separate, independently-testable `render.render` calls instead of one large one.

## Page content (`page.lua`) -- and why it's not the extension canvas

`html.lua` already has a typed-table -> renderer mechanism for *untrusted* content: the extension canvas (`html.validate_canvas`/`html.render_canvas`, vocabulary `heading`/`text`/`table`/`button`). Its entire reason to exist is being a narrow **trust boundary** -- a plugin's page is restricted to that closed vocabulary specifically so deployment-authored extension code can never emit arbitrary HTML/JS. Its own header comment says to grow that vocabulary "only when a real plugin needs a new element type... not speculatively" -- narrowness is the point, not an oversight.

`page.lua` is the same *pattern* (typed section table -> dispatch-by-type renderer, string leaves through `render.lua`) applied to daat's own first-party pages instead -- a completely separate module, vocabulary, and code path, with no security boundary to protect (every caller is trusted core code, not an attacker). Sharing one vocabulary between the two would mean either crippling core pages down to the canvas's deliberately tiny set, or growing the canvas to match core's real needs and handing extensions that same expanded surface -- both wrong, for different reasons. Never add a section/element type to one because the other needs it.

`page.lua`'s own vocabulary grows the same way the canvas's and `template.lua`'s did: only when a real page actually needs a new section type. Current vocabulary and what motivated each addition: `form` (`html.render_login`); `subheading` and standalone `message` (`html.render_account` -- headings and a message banner that sit *outside* any form, unlike login's, which are form fields); `table`, and a form field's `value`/`placeholder`/`size` attributes plus an optional (not required) `label` (`html.render_admin_users` -- a dynamic per-row table whose cells hold compact, label-less inline forms); `secret_reveal` (`html.render_admin_api_keys` -- a one-time "here's a secret, it won't be shown again" banner, bold instruction text plus a distinct `<code>` value, a genuinely different shape from `message`'s single escaped string). A `form` section's fields support `text`/`password`/`hidden` (the CSRF token needed a way to appear with no visible label); `submit_class` lets a form pick "btn-primary" (default) or "btn-secondary" (account's Log out button, admin-users'/admin-api-keys' per-row "Set"/archive actions) since not every submit button is the primary action on its page.

**A field's `label` is optional, and that changes what else renders.** `html.render_login`/`html.render_account`'s fields all had a real `<label>`; `html.render_admin_users`'s compact per-row/create-user fields use `placeholder` instead and have no visible label at all. `render_page_field` skips the `<label>` line when `field.label` is `nil` -- and skips the input's `id` attribute too, not just the label, since an `id` with no `<label for="...">` pointing at it is dead markup the original never had. Don't default `id` to "always present" the way `autocomplete`/`required` safely can; it's the one attribute whose only reason to exist depends on something else (the label) also existing.

**A table cell can only nest a `form` section, not any section type generally -- deliberately, not as a TODO.** `render_page_table`'s per-cell items dispatch straight to `render_page_form`, not through the generic `render_page_section` dispatcher (see the next gotcha for why), and `validate_section`'s own cell-item check is kept in sync with that same restriction rather than accepting something render would silently drop. Broaden both together, in the same change, if a real page ever needs a different type nested in a cell -- don't widen one without the other.

**A second, sharper form of the same forward-reference gotcha: mutual recursion between two different functions, not just one function referencing a later constant.** Converting `html.render_admin_users` needed a table whose cells can contain forms (`render_page_table` calls into form-rendering) where a `table` section can itself appear at the top level (`render_page_section` dispatches out to `render_page_table`). Writing that the "obvious" way -- both functions defined once, each calling the other by name -- put `render_page_table` textually *before* `render_page_section`, so `render_page_table`'s own call to `render_page_section` hit exactly the `doc/templating.md`-documented trap: an unset global, not a forward reference, crashing only when a table section is actually rendered (`attempt to call global 'render_page_section' (a nil value)`), not at build time. Unlike a single function calling *itself* recursively (safe -- by the time the body executes, its own `function name(...)` assignment has already completed), two distinct functions that call each other can't both be defined "after" the other no matter how you order them. The fix here was to avoid the mutual recursion entirely: `render_page_table` calls `render_page_form` directly (a plain backward reference, since only `form` ever nests in a cell -- see above) instead of going through the generic dispatcher. If a future case needs genuine two-way recursion between named functions, the real fix is forward-declaring one of them (`name = nil` before both definitions, so the second definition reassigns the same already-declared local rather than each `function name(...)` statement being its own fresh implicit-local) -- untested in this codebase so far; avoiding the mutual recursion, like this one did, is the simpler and lower-risk option when it's available.

**A verification-script bug that looked like a real regression: filter out variable *values* by substitution, not variable *lines* by dropping them.** Converting `html.render_admin_api_keys` (a one-time "save this key now" banner, new section type `secret_reveal`), the normalized diff showed the entire banner missing from the post-migration output -- alarming, since nothing in the page.lua change should have dropped it. The actual cause was in the diff script, not the page: it stripped any line containing `<code>` to neutralize the random secret-key value before comparing. The pre-migration markup pretty-printed the banner across four lines (the `<code>...</code>` value alone on its own line), so that filter removed only the value line; `page.render`'s output is compact -- the whole banner is one line -- so the same filter removed the *entire* banner, div and instruction text included, from only one side of the diff. Fix: normalize by substituting the variable part with a placeholder (`sed -E 's/[0-9a-f]{32,}/HEXVALUE/g'` catches every random hex token -- CSRF values and secret keys alike -- regardless of what tag or line it's sitting in) rather than dropping any line that merely *mentions* the marker. A page.lua conversion is verified when the *tool* is trusted, not just when its output looks clean -- when a diff shows something alarming, check whether the diff script itself is the thing that changed behavior before concluding the code did.

**Attribute order can legitimately differ page to page, and that's fine to leave alone.** `html.render_login`/`html.render_account`'s original markup put a form's `class` before `method`/`action`; `html.render_admin_users`'s put `method`/`action` first -- an inconsistency that already existed in the hand-written markup before any of this migration, not something introduced by it. `page.lua` picks one order and applies it everywhere, which happens to byte-match the first two pages and not the third. That's a real, visible diff in a before/after comparison -- checked and confirmed harmless (HTML attribute order carries no meaning) rather than silently ignored. Don't spend effort matching it; unifying to one consistent order is arguably a small improvement, not a regression to fix.

**`page.validate` failures are not a real error path, unlike `template.validate`/`html.validate_canvas`.** Those two validate genuinely external/untrusted data (a deployment's template file, an extension's `render()` return value) where a malformed result is expected and handled by propagating `nil, err` onward. `page.validate` only ever checks a literal section table daat's own code just built a few lines above the call -- a non-nil return means a real bug in daat's own source, not a data problem, so callers `error()` on it immediately rather than threading it through as a return value.

**CSS class duplication found but deliberately not fixed in this pass**: login's message banner uses the shared `.platform-error-banner` class; account's uses its own page-specific `.platform-account-message`/`-error` classes -- two different, never-unified ways to style what's conceptually the same "message banner" shape. `render_page_message` centralizes the *rendering* (both now go through the same function), but takes the CSS class name as a caller-supplied argument rather than forcing one shared class -- unifying the CSS itself is a separate, later decision (visible-output-changing, not a pure refactor) and shouldn't be bundled into a structural migration that's otherwise byte/DOM-verifiable.

**A real gotcha hit converting the first page, worth knowing before converting the next one:** a Luam triple-quoted string (`"""..."""`) strips a newline immediately after the *opening* `"""` (the same long-bracket-string rule real Lua's `[[` has), but does **not** strip a trailing newline before the *closing* `"""`. Composing two such strings back to back (an inner section's rendered output, itself ending in `\n`, embedded into an outer page template that also puts a literal `\n` before what follows) silently produces a doubled newline -- a spurious blank line in the output, easy to miss by eye and only caught by a byte-level diff against the pre-migration output. When composing a `render.render` result into another template, check whether the inner result already ends in `\n` before also putting a static `\n` after its placeholder in the outer template.

**Verification method for any page conversion**: capture the real CGI response for the page (all its meaningfully different states, e.g. login's with-error/without-error, account's none/error/success) *before* touching it, convert, rebuild, capture again, and diff. For a page whose sections render at the same nesting depth as before (login: the form was already the page's sole top-level content), a raw byte diff modulo the known-nonvariant fields (CSP `nonce`, `Content-Length`, a fresh CSRF token value) should come back clean. For a page where `page.lua`'s fixed section indentation doesn't match the original's nesting depth (account: its forms sit one level deeper, inside `.platform-account-card`, than `page.lua`'s renderer assumes), normalize whitespace before diffing (strip leading/trailing space per line, drop blank lines) rather than accept a dirty raw diff as "close enough by eye." This is still a real, rigorous check, not a weaker one: it caught a genuine bug converting `html.render_account` -- the Log out button silently lost its `btn-secondary` class (rendered `btn-primary` like every other submit button) until `submit_class` was added specifically because the normalized diff surfaced the one real line that actually differed.

**That per-page diffing verifies one page's happy/error paths, not `page.lua` itself -- `tst/unit/page.lua` covers the module directly.** Five real pages' worth of before/after diffing never once exercised most of `page.validate`'s own error branches (a page's section list is always well-formed by the time it's handed to `page.validate` -- that's the whole point of building it in code) or the finer render-time distinctions (nil vs. `""`, a checkbox's reversed label order, a textarea's value-as-inner-content). `tst/unit/page.lua` (same convention as `tst/unit/template.lua`: `require("page")`, a `check()`/`FAILURES` counter, one `test_*` function per behavior) tests `page.validate`/`page.render` directly against constructed section tables, independent of any one page -- including regression locks for both bugs this session's consistency pass found (the missing `heading`/`message`/`css_class`/`submit_class`/table-`css_class` validation, and `attr_fragment`'s nil-vs-`""` fix). Extend this file, not a sixth page's own bats test, when the thing being checked is a property of the vocabulary itself rather than one specific page's content.

**`html.render_settings` forced the biggest vocabulary jump so far: a form visually split into named sections, and three new field types.** A settings-style page can't just be a flat field list -- HTML forms can't nest, so "one real `<form>`, several visually distinct headed sections inside it" needed a real new concept, `form.groups` (a list of `{css_class, heading, intro?, fields}`, each rendered as its own `<div>` with an `<h3>` inside the one outer form) alongside `form.fields` (still there, for anything that isn't part of a visible group -- the CSRF hidden field). New field types: `checkbox` (the one type whose `<label>` comes *after* its input, not before -- matches how a checkbox actually reads), `file` (adds an `accept` attribute), `textarea` (its value is escaped *inner content*, not a `value=` attribute, the one field shape that isn't a self-closing `<input>`). Also added: a field's own optional `wrapper_class` (wraps that one field's label+input pair in a div -- a checkbox needs its flex-row wrapper, each color field needs its own grid-item wrapper) and a group's separate `fields_wrapper_class` (wraps the group's *entire* field list in one more div -- the Colors group's shared grid container around all of its color fields together). Two different things named similarly on purpose: one wraps a single field, the other wraps a whole group's worth.

**A real bug in `attr_fragment` itself, not in any one page's conversion: `nil` and `""` are not the same "absent."** `attr_fragment` originally treated an empty string exactly like `nil` -- both omitted the attribute. That was invisible through four page conversions because none of them ever had a text field whose value was genuinely present-but-empty. Settings' color fields are exactly that case: an unset color is a real, empty string the original always rendered as `value=""` (so the browser and any client-side JS sees a real, present, empty field) -- my version silently dropped the attribute entirely instead, caught immediately by the tag-boundary-normalized diff across every one of the fourteen color inputs at once. Fixed by making `attr_fragment` treat only `nil` as "the caller doesn't want this attribute" -- an empty string is a real value and renders as one. This was a latent bug in already-shipped conversions too (an admin-users/admin-api-keys row for a user or key with a genuinely empty `cap` string would have hit the same silent omission), just not one any of that migration's test data happened to exercise -- the fix improves those pages' correctness as a side effect, not just settings'.

## A consistency pass found two real gaps, worth naming as a general check

Auditing `validate_section` against what `render_page_form`/`render_page_table` actually read turned up four fields used at render time but never checked at validate time: `form.heading`, `form.message`, `form.css_class`, `form.submit_class`, and `table.css_class`. All five now get the same "optional; a non-empty string if given" check every other optional field (`label`, `intro`, `wrapper_class`, `enctype`...) already had. This is exactly the class of drift `page.validate`'s own existence is supposed to prevent -- an empty-string `heading` wouldn't have crashed anything, it would have silently rendered `<h2></h2>` and looked like a bug report waiting to happen. Separately, `css_class_attr` was being built by raw string concatenation in two places (`render_page_form`, `render_page_table`) instead of going through `attr_fragment` like every other optional attribute -- harmless in practice (a `css_class` value is always a trusted literal, never user data) but a real, avoidable inconsistency; normalized to `attr_fragment("class", section.css_class)` in both places. **The general lesson: whenever a new optional section/field property is added, grep render for every `section.x`/`field.x` it reads and confirm validate checks each one -- it's an easy pair to let drift apart one commit at a time**, exactly as happened here across five separate migrations before anyone checked the two against each other directly.

**`html.render_sql`'s query form needed nothing new; its results table needed a genuinely different kind of cell item, and exposed two attribute gaps.** The query box is exactly `form`+`textarea`, already built for settings -- zero new vocabulary. The results table is different: `display_value`/`render_reference_value` both return already-escaped or already-built HTML (a reference column is a real popover-linked `<a>`, not plain text) -- a plain string cell item would have HTML-escaped that a second time into visible markup. New type: `html_fragment` -- `{type = "html_fragment", html = "..."}`, inserted verbatim. Named for what it holds, deliberately *not* "raw": `render.lib`'s own `{{{ }}}` already uses "raw" as an escaping-behavior adjective, and reusing that word as a formal vocabulary type name (the kind of thing that shows up in a validation error message or a doc heading) read as vague rather than clear -- caught by a direct question before it shipped, not a style nitpick added later.

Converting this one page also exposed two attribute gaps neither of the first five pages had needed: a field's own `css_class` (some CSS -- `.platform-sql-input` -- targets the `<input>`/`<textarea>` element directly, not a wrapper div around it, which is all `wrapper_class` ever gave a field) and an explicit `id` override (`platform-sql-query`'s id exists purely for client-side JS to find that exact element, with no `<label>` involved at all -- the existing "id only when labeled" default had no way to express that). Both got mirrored onto `table` too (`wrapper_class` as a real wrapping `<div>` distinct from `css_class` on the `<table>` element, plus `id`), since the SQL console's own `.platform-table-wrapper` is a wrapping div's class while `#sql-table` is the table's own id, not a class -- the same class/wrapper_class split fields already needed, one level up.

**Two real mistakes in this same slice, neither caught before testing:** (1) three `<p class="platform-empty">`-shaped messages (no rows, an empty submitted query, the real row count) were written as direct `render_lib.render(...)` calls rather than page.lua sections -- correct call, but `render_lib` itself was never `require`d in this function, since the rest of the conversion only ever needed `page_lib`. Crashed exactly those three states with "attempt to index global 'render_lib' (a nil value)," caught immediately by testing all five states rather than assuming the two that happened to work first proved the rest. (2) While building a throwaway schema to get realistic reference-column data for a baseline, a schema field was written with `ref_entity_type` as its key -- not `entity_type`, the real convention used everywhere else in the codebase (`doc/schema.md`, `examples.lua`, `document.lua`, every existing test fixture). The original code failed against that self-invented, incorrect schema, which looked exactly like a real bug in `schema.lua`'s own field-registration -- "fixing" it (reading `field.ref_entity_type` instead of `field.entity_type`) broke two real, already-passing tests immediately. Reverted the moment the failures made the actual convention obvious. The lesson isn't "double-check schema.lua" specifically -- it's that a plausible-looking bug found while building throwaway test fixtures deserves the same "grep the whole codebase for the real convention first" scrutiny as one found in the thing actually being changed, before treating it as confirmed and touching a file outside the current task's real scope.

## Scope boundary: where page.lua stops paying for itself

The remaining `html.lua` page content -- the registration grid, the chat widget, the knowledge graph explorer -- was described earlier as "a different kind of harder... live client-side interactivity, not just a bigger static vocabulary." Looking at each one directly instead of assuming sharpens that into an actual rule, not just a hunch. (The SQL console turned out to be the exception that proves it -- see below: mostly static structure after all, converted with one small, real vocabulary addition, not left on this list.)
- **The registration grid (`html.render`) turned out to be mostly correct as "separate design work," but not all-or-nothing.** Its table body/headers are never server-rendered at all -- `<tr id="table-headers">`/`<tbody id="table-body">` ship empty on the wire; `initTable()` builds every header and row client-side from the same `layout` JSON already being injected into the page's own `<script>` block. There's no real per-row/per-cell *data* for `page.lua`'s `table` type to describe here (forcing one, with zero rows, would mean pre-rendering real `<th>` elements the original never sent on the wire -- a visible-output change, which the design plan's own non-goal explicitly ruled out). The CSS block and the ~140-line templated inline `<script>` are, correctly, not `page.lua`'s job at all -- see the general rule below. What *did* convert: the two small pieces of static shell that genuinely recur, byte-for-byte in shape, at exactly one other real call site (`html.render_entity_edit`, the single-row edit page) -- a plain (non-submit) button group and an empty, JS-filled status placeholder div. Two new section types, `actions` (`{buttons = {{label, id, css_class}, ...}, style?}` -- `style` is a deliberate, rare exception to the usual class-only convention: the edit page's own action group needs inline `margin-top: 20px` its neighbor doesn't provide, register's doesn't since its own neighbor already carries `margin-bottom`) and `status_placeholder` (`{id, css_class}`, always empty). Verified via a real `/register?type=<schema>` capture, before/after, fully whitespace-stripped diff (not just tag-boundary-normalized -- an HTML comment inside the untouched table shell doesn't split cleanly on `>`/`<` boundaries the way every other page's markup has so far) -- clean. `html.render_entity_edit` (the single-row edit page these two types were named for as a real second call site) converted the same way immediately after, with genuinely zero new vocabulary needed -- same verification method, same clean result.
- **The chat widget and knowledge graph explorer are mostly client-rendered already.** Message history re-renders from polled/fetched JSON, not server-side HTML; the graph is an SVG built entirely by client-side JS from `/knowledge-graph-data`. There is very little static, recurring *structure* left to describe once the interactive core is set aside -- forcing what's left through `page.lua` would add ceremony (a typed table, a validate call, a render dispatch) without buying back the thing that vocabulary is actually for: preventing the same shape from drifting out of sync across *multiple* call sites. Each of these is a unique, one-off widget with exactly one call site. Left as bespoke string-built HTML+JS, on purpose, not as an oversight.

**The general rule this makes explicit, not just for these four pages:** `page.lua` describes *structure that recurs* -- the same shape, written more than once, that can drift out of sync. A page's live *behavior* -- event handlers, polling, drag/zoom, autocomplete -- is never something to encode as vocabulary; it stays external JS, addressed by class/id/data-attribute the same way `html.canvas_js` already keeps a plugin's behavior separate from `html.render_canvas`'s declared structure. A one-off widget with a single call site doesn't need this pattern at all, no matter how complex its markup -- there's nothing for a shared vocabulary to keep *in sync*. The registration grid sharpens this further: even a page that's mostly *not* a fit can still have a small, genuinely recurring piece worth converting on its own -- "separate design work" doesn't have to mean "all or nothing," it means look at what actually recurs rather than deciding by the page's overall shape.

## What this doesn't cover (yet)

Converting a page to `page.lua` sections is real, page-by-page work tracked on the brex backlog, not a single migration. Done so far, in order, each proving out a real new piece of the vocabulary against a real page rather than a hypothetical one: `html.render_login`, `html.render_account`, `html.render_admin_users`, `html.render_admin_api_keys`, `html.render_settings`, `html.render_sql`, and (partially -- action-button-group and status-placeholder shell only, in each case) `html.render`/`html.render_entity_edit`. The second of those two needed zero new vocabulary, exactly as predicted when the first one shipped -- `actions.style` (inline `margin-top: 20px`) is why it exists at all: entity-edit's own fields list carries no bottom margin of its own the way register's table-wrapper neighbor does. The chat widget and knowledge graph explorer are deliberately out of scope for this pattern -- not "not yet," genuinely not a fit.
