# Why an Owned Agent Loop, Not an Off-the-Shelf Harness

daat's chat agent doesn't run on a model provider's own managed agent SDK (e.g. Anthropic's Claude Agent SDK, OpenAI's Assistants/Agents API) or a third-party orchestration framework (LangChain, AutoGen, CrewAI, and the like). `src/agent.lua` calls the model as a plain, low-level completion service (`doc/agent-protocol.md`'s `generate`/`converse`/`embeddings` interface) and owns the entire turn loop, tool dispatch, and approval flow itself. This document is the reasoning: not that adopting one of these was impossible, but that daat's actual requirements don't fit the shape either kind of off-the-shelf harness assumes, closely enough that building the loop directly ends up being the more direct path to what the system actually needs.

## Approval has to survive past the end of the request that triggered it

A destructive tool call (`entity.create`/`update`/`archive`, `document.create`/`update`, `knowledge.distill`) can't execute without a human approving it first, and that approval is a real, persisted, two-phase state, not a blocking prompt or an in-process callback: a single web request can't pause mid-call waiting on a person's real-world response time, so the request that proposes a destructive call returns immediately, and a *separate, later* request -- the human clicking Approve or Deny in the chat widget, possibly minutes or hours afterward -- is what actually executes it or records the refusal (`agent.create_pending_action`, `src/agent.lua:1720`, backed by the `agent_pending_action` table, `src/agent.lua:75`). See `doc/architecture.md`'s "Chat" and "Agent control: rule-based by default" sections for the full mechanism.

A managed harness's own tool-calling loop is built around resolving a tool call as part of finishing one turn -- synchronously, or via an async callback the loop awaits -- within a single logical run. Neither shape has a natural place to say "stop here, persist this exact state, and don't resume until an unrelated HTTP request arrives an indeterminate amount of time later." Getting that behavior out of a framework not built for it would mean fighting its own control flow at exactly the point where getting it wrong is a real safety property, not a convenience feature.

## The exact prompt, reasoning, and tool calls are source data, not exhaust

Every real model call -- a chat turn, the compaction summarization call itself -- has its exact prompt (system prompt plus assembled history, verbatim), model id, and real token counts persisted (`knowledge_context`, described in `doc/architecture.md`'s "Knowledge pool" section). A reply that leaks visible reasoning gets that reasoning split out into its own document and run through the *same* tiering/retrieval/decay pipeline as anything else in the pool, not a separate log nobody looks at again. This is only possible because `agent.lua` sees the raw request and response at every step -- there's no framework-owned conversation object in between whose internal state would need to be reverse-engineered or specially exported to get the same data out.

## One neutral protocol, several interchangeable vendors, by config not by code

`doc/agent-protocol.md` is `agent.lua`'s own tool-calling contract -- plain JSON Schema, not any vendor's dialect -- that `agent_provider_vertex.lua`, `agent_provider_claude.lua`, and `agent_provider_test.lua` each translate into and out of. Which provider runs is a `platform.lua` config value, not a code change. A provider's own managed agent SDK is inherently built around that provider's own tool-calling conventions; adopting one either locks daat to that vendor or requires building the same kind of neutral translation layer on top of it that `agent_provider_*.lua` already is -- and at that point the SDK's own loop isn't saving the hard part, since the hard part (the neutral protocol and its per-vendor translation) still has to be designed and owned directly either way.

## A sub-agent's tool list is narrower by construction, not wider with instructions to behave

`research.investigate`'s isolated sub-loop declares every non-destructive `AGENT_TOOLS` entry except `research`/`clarify`/`background` themselves to the model -- it isn't told not to call those, it's never told they exist, so a bounded, read-only sub-investigation can't escalate scope or spawn further unbounded work (see `doc/architecture.md`'s "Agent control: rule-based by default"). That's a structural property of `AGENT_TOOLS` being an ordinary Lua table `agent.lua` constructs per call, not a globally registered plugin set. Getting the identical guarantee out of a framework's own tool-registration model would mean confirming, and then trusting, that its exact registration semantics support a genuinely different, dynamically-narrowed tool list per invocation -- rather than the few lines of code this already is.

## Minimal dependencies applies to the harness layer too

`doc/why-luam.md`'s "Minimal dependencies, not just a minimal grammar" section documents this as a load-bearing property elsewhere in the stack: `bcrypt`, `sqlite`/`mariadb`, and `socket` are all vendored directly in Luam's own `lib/`, not pulled from a package manager's dependency graph. An agent SDK or orchestration framework is a real dependency by the same standard -- its own versioning, its own breaking changes, its own bug surface sitting between `agent.lua` and the raw model API -- for a piece of the system (the turn loop and tool dispatch) that, once the neutral protocol above is designed, is not large: `agent.lua`'s own `run_turn` is a bounded loop over a handful of well-understood steps, not the kind of general-purpose orchestration surface a framework is built to cover.

## What this costs, and what it buys

The tradeoff is real, not one-sided: a managed framework brings retry/backoff handling, streaming ergonomics, and a wider ecosystem of pre-built integrations that `agent.lua` has to implement or do without. What it buys back is full control at every decision point that's actually safety- or provenance-critical for this system -- the approval gate, the knowledge-pool feed, vendor neutrality, and sub-agent scoping above -- expressed as ordinary, readable Lua in one file instead of behavior that has to be configured into, or verified against, a general-purpose framework not built around any of those four requirements specifically.
