# Why Luam

daat is written in [Luam](https://github.com/BenSiv/luam), a fork of Lua 5.1. Luam's own reasoning for existing is written down in [its manifesto](../../luam/doc/manifesto.md) -- eight tenets, each one either inherited straight from Lua's own stated design goals or a continuation of that same instinct applied somewhere Lua itself stopped short. This document is the other half of that: where each tenet actually shows up in daat's own code, and why a more permissive language would have made the same result a harder, less direct fit -- not impossible, just an unnecessary hurdle for what the job actually needs.

[doc/prior-art.md](prior-art.md) covers the other side of the same question -- the off-the-shelf wikis and LIMS-style platforms that could have been the base instead, and the specific technical requirements each one fell short on. The short version, needed below: extensibility and AI-native retrieval were the two requirements almost nothing existing was built to support directly, and a system built to host an agent as a first-class actor needs a scripting layer where "presence or absence" and "scope" are never ambiguous -- exactly the properties a fork of Lua can guarantee at the language level and a general-purpose scripting language typically can't.

## One generic type, from a developer's source file to a user's schema (tenet 2)

Luam is not a configuration format or a domain-specific language that happens to also be usable for real development -- it's the other way around: a general-purpose language (loops, functions, closures, a full standard library, everything Lua itself is) with the redundant alternatives subtracted out, per the manifesto's own tenets 4 and 5. That's what makes it usable as a schema/config authoring surface *without* being purpose-built as one. Lua's own "vivid expression of its simplicity," in its creators' words, is offering one composite data structure -- the table -- instead of a separate built-in for arrays, records, sets, and objects. Add a handful of primitives (`nil`, boolean, number, string, function) and that's the entire vocabulary, for everyone who ever touches daat: the person writing `src/agent.lua` and the person defining a new entity type for their own deployment are reaching for the exact same construct, not two different ones scoped to two different audiences.

**A schema, a config file, and a data record are the same shape.** A schema definition (`schemas/reagent.lua`) is a table -- `{name = "reagent", fields = {{name = "lot_number", type = "text", required = true}, ...}}`, validated field-by-field in `schema.validate` (`src/schema.lua:293-384`) against a closed `FIELD_TYPES` list (`src/schema.lua:13`). Platform config (`theme.lua`, `platform.lua`) is the same convention -- a table of settings, loaded and validated the same way (`src/config.lua:15-24`). An entity record fetched back out of the database (`entity.get`, `src/entity.lua:634-646`) is, again, a plain table -- one field per column. None of these three needed their own representation; the same generic type serves a schema *description*, a *configuration*, and the *data* that schema describes.

**The same type also serves as the executable structure, not just the descriptive one.** An extension's `main.lua` returns `{on_before = function(new, old, ctx) ... end}` -- a table whose values are functions, looked up by hook name and called directly (`hook_fn = hooks[hook_name]; ... pcall(hook_fn, ...)`, `src/extension.lua:313-316`). `AGENT_TOOLS` in `src/agent.lua` goes further: it's simultaneously a JSON-Schema-shaped protocol description (`parameters = {type = "object", properties = {...}, required = {...}}`, documented at `src/agent.lua:695-702` as "daat's own neutral tool-calling protocol... not any one vendor's dialect") *and* the live dispatch/lookup structure the platform indexes directly -- `agent.is_known_tool`/`agent.is_destructive` (`src/agent.lua:1063-1077`) walk straight into it, and `src/provider/agent_claude.lua`'s `claude_tools_from_canonical` and Vertex's own converter each project a different vendor-specific view from that one table. There is no separate "here's the schema, and here's the code that implements it" pair to keep in sync by hand, because there's only one artifact.

**Why one language, not a restricted one for users and a real one for developers.** The usual alternative -- a config format (YAML/JSON) for the person defining a schema or extension, and a real programming language for the person building the platform -- buys perceived safety at the cost of a second parser, a second vocabulary, and a hard line between what each audience is allowed to understand. daat doesn't need that trade: `doc/schema.md`'s own framing is that a definition file is "executable, not inert data the way a YAML/JSON file would have been... Same security posture a data format would have had, without needing a second parser to get there" -- the safety a restricted format would have bought is already supplied by `sandbox.lua`'s meta-mechanism (tenet 3, `getfenv`/`setfenv`), which hands a loaded schema, config, or extension file a genuinely restricted environment (`config.lua:15-24`: "no io/os/require/loadstring/network, just pairs/ipairs/string/table/math") -- so the restriction is a capability set the platform controls per file, not a different, smaller language the user is stuck with. A JSON schema can't validate itself against a closed type list the way `schema.validate` does; a YAML extension manifest can't express `events = {"entity.before_create"}` as anything richer than a string the platform has to separately parse meaning back out of.

That makes the user a first-class citizen of the same language the platform itself is written in, not a guest confined to a simplified dialect of it. The on-ramp is a single continuum, not three separate skills: someone who has only ever edited `theme.lua` to change a color already knows the table-and-field vocabulary a `schemas/*.lua` file uses; from there, an extension's `manifest.lua` plus a `main.lua` returning `{on_before = function(...) end}` is the same vocabulary again, just with functions in the table instead of only values; and from *there*, `daat`'s own `src/schema.lua` or `src/extension.lua` -- the code doing the validating and dispatching -- is still nothing but that same table-and-function vocabulary, now read instead of written. Configuring the system, extending it, and developing its core aren't three languages a user has to be handed off between as their needs grow -- they're one thing, done at increasing depth. Two separate languages (a restricted one for users, a real one for developers) would put a hard ceiling on that progression by design, since crossing it would mean throwing away everything already learned and starting over in a different language. This is what [prior-art.md](prior-art.md) means by extensibility as a hard requirement: not just that a deployment *can* add behavior, but that picking up how gets a user closer to the platform's own core, not shut out from it.

## One way to do a thing, enforced by the grammar (manifesto tenets 2, 4, 5)

Luam's manifesto states this as a general principle: remove the alternative instead of documenting a preferred one. In daat's own `src/`, that shows up as:

- **One way to introduce a variable.** `local` is gone; bare assignment is implicit-local everywhere except the REPL -- and a bare `function name() ... end` gets exactly the same treatment as `name = function() ... end`, rather than being a second, global-writing idiom sitting next to it. There's no "did they mean to leak this" question to ask in review, because leaking it takes a deliberate `_G.name = ...`, not a forgotten keyword.
- **One way to call a function on a table.** Colon method-call sugar is removed; it's `obj.method(obj, ...)` or nothing. daat's `src/` is eighteen modules, every one a plain table (`db = {}`, `sandbox = {}`, `cgi = {}`), because the language doesn't offer a second idiom to drift toward.
- **One boolean, no stand-ins.** `if`, `while`, and `not` require an actual `true`/`false`. That single rule is why `src/` has explicit `!= nil` checks well over 200 times, in nearly every file -- presence-or-absence is asked as its own question, never inferred from coercion. For a system whose core promise is full audit provenance -- entity history, archived-vs-active state, tier and heat computation that must never silently misfire -- removing the "is this nil, false, or just zero" ambiguity at the language level closes off a whole category of bug before it can reach the ledger. It isn't a standing runtime cost either: when the compiler can already prove a value is boolean, the check is skipped entirely.
- **One `load`, and the primitives kept for sandboxing (tenet 3).** `sandbox.lua` -- daat's entire trust boundary for schema files, extension manifests, and extension hooks -- leans on `load`/`loadstring` plus `setfenv`, binding untrusted source to a restricted environment table before it's ever called. Luam kept `setfenv`/`getfenv` and the underlying metatable machinery enabled at the primitive level specifically for this. daat's extension system is that scenario running in production: no second language runtime, no subprocess boundary, no separate C-level sandbox to build and audit.

## Minimal dependencies, not just a minimal grammar (tenet 7)

The same instinct extends to what ships with the language. Luam's `lib/` is where daat gets nearly every dependency it has below the web layer: `auth.lua` calls `require("bcrypt")` directly for password hashing; `db.lua` sits on Luam's own `database` module spanning both SQLite and MariaDB; `sandbox.lua` reaches for `require("socket")` only when an extension's manifest actually declares outbound-network capability; `cgi.lua` pulls in `dkjson` and `paths`. None of that came from a package manager's dependency graph -- it's built and versioned as one artifact alongside the language itself, the same guarantee Python's pip/venv/poetry/conda four-way split and JavaScript's npm depth don't offer.

## A single small binary matches a single self-contained application (tenet 1)

daat builds to one binary that dispatches, per invocation, into CLI commands or CGI-style web-request handling. Luam's changelog reports source size within 0.3% of upstream Lua 5.1 and a stripped interpreter around 215KB. That's what lets daat actually be the single, self-contained thing its README claims -- no external identity system, no separate version-control layer, nothing beyond a couple of documented runtime tools (`cmark-gfm`; `curl`/`gcloud` if chat is enabled) -- rather than a thin wrapper shipping a general-purpose language runtime, and its packaging ecosystem, as a hidden second dependency.

## Why not Python or JavaScript

Both are realistic, mainstream choices for a project like this -- not passed over for being obscure or unfamiliar.

**Python** states the same goal Luam pursues -- "there should be one obvious way to do it" is literally a line from its own Zen -- but treats it as a style aspiration rather than something the compiler enforces, so the alternatives it warns against exist anyway and are common idiom: f-strings, `.format()`, and `%`-formatting all still work; dataclasses, namedtuples, plain dicts, and full classes all still compete for the same job; `if not items:` relying on an empty list's truthiness is standard style, not a warning. That last one is exactly the ambiguity Luam's strict conditionals refuse to allow at all -- Python leans into the same coercion Luam's manifesto calls out as a bug class, rather than closing it off. And where daat wants "minimal dependencies" as a load-bearing property, not a preference, Python's own packaging story is its most famous counter-example: pip, venv, poetry, and conda are four live, mutually-incompatible answers to the same "how do I install a dependency" question, and embedding CPython itself -- the actual interpreter, not just the ecosystem around it -- is a far heavier, far less embeddable proposition than Lua's own stated design goal of fitting on a floppy disk.

**JavaScript** can't apply manifesto tenet 4 -- "subtraction is allowed to be the feature" -- even if a future version of it wanted to, because "don't break the web" is a hard platform constraint: every alternative the language has ever grown (`var`, then `let`, then `const`; four-plus ways to define a function or method; `==` against `===`) has to stay forever, because some page somewhere might depend on it. That's the literal opposite of what a fork gets to do. The practical cost of that is the same scoping-and-coercion ambiguity Luam's strict conditionals and implicit-locals close off by construction: a variable captured by reference instead of value inside a closure, or a value that's `0`/`""`/`undefined` silently standing in for "false," are both classic JavaScript footguns the language has no way to retire, however well understood they are. And npm's dependency trees -- a small utility function once famously shipped as its own package with its own transitive dependents (the `left-pad` incident) -- are the "minimal dependencies" principle's most public failure, in the same ecosystem that would have been the alternative to Luam's own `lib/`.

Neither comparison is about Python or JavaScript being bad languages -- they're general-purpose languages doing what general-purpose languages are for, which is supporting many different kinds of programs at once. That breadth is exactly the property [prior-art.md](prior-art.md) finds becoming a wall, in different forms, across every platform surveyed there.
