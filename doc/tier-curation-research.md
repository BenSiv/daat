# Tier curation research

`TIER_JUDGMENT_SYSTEM_PROMPT` already went through one redesign -- agent-gated tier promotion instead of a fixed `content_shape` formula (task #87/#118; see `architecture.md`'s "Knowledge pool" section). That redesign fixed *how* a tier gets decided (a model judgment call, not a mechanical mapping) but left *what each tier actually means* almost entirely implicit, defined mostly by a one-line label ("Curated Draft", "Developed Reference", "Atomic Record") plus whatever the model inferred from that label. This doc covers a second pass: making each tier's definition explicit enough to hold up against real content, informed by (1) external research into how other knowledge-management systems draw comparable lines, and (2) concrete misclassification patterns found while dogfooding tiering against a real deployment's knowledge pool. Same kind of investigation `prior-art.md` did for the platform as a whole, scoped here to just the tiering scheme. (Deliberately keeping this write-up domain-agnostic, same as the rest of daat's own core -- see `architecture.md`'s "No domain vocabulary in core" -- the specific deployment's own data, names, and content stay out of this repo; only the general shape of each failure mode is documented here.)

## External prior art: is a four-tier ladder even the right shape?

Before tightening the four existing tiers, it's worth asking whether four tiers -- Raw Intake / Curated Draft / Developed Reference / Atomic Record -- is the right structure at all, or whether an established knowledge-management scheme does this better.

**[Zettelkasten's fleeting/literature/permanent notes](https://zettelkasten.de/posts/concepts-sohnke-ahrens-explained/)** is the closest match, and validates daat's overall shape rather than replacing it. Fleeting notes (quick, disposable captures) map to Raw Intake; literature notes (paraphrased summaries of a source, in the reader's own words but still tied to that source) map to Curated Draft; permanent/evergreen notes (a single idea, stated so it stands independently of its origin, densely linked to other permanent notes) map directly to Atomic Record. Zettelkasten has no real equivalent of Developed Reference -- a "big wiki article" isn't a shape its method produces -- but that's a gap daat's own domain (a lab's shared knowledge base, not one person's personal note archive) actually needs filled, not a sign the extra tier is wrong. The "densely linked" requirement Zettelkasten places on permanent notes is handled by a separate mechanism entirely in daat (`document_link`/co-retrieval linking, spreading activation -- see `architecture.md`), not folded into the tier definition itself.

**[Wikipedia's content-assessment scale](https://en.wikipedia.org/wiki/Wikipedia:Content_assessment)** (Stub -> Start -> C -> B -> Good Article -> Featured Article) is far more granular than daat's single Developed Reference bucket, and its Stub-to-Start boundary is exactly the line this pass needed for Tier 2: a long dump doesn't clear even Start-class without real editorial organization imposed on it, regardless of how much text it contains. Wikipedia's finer C/B/GA/FA gradations above that aren't worth importing into daat -- they're calibrated for community peer review at Wikipedia's scale, not a single model judgment call on a lab's internal notes -- but the underlying principle (length and structure are necessary, never sufficient, for "developed") is exactly what Tier 2's definition was missing.

**[Progressive Summarization](https://fortelabs.com/blog/progressive-summarization-a-practical-technique-for-designing-discoverable-notes/)** (Tiago Forte) distills a source through discrete, strictly additive layers -- Layer 0 is always the full raw source, then a bold pass, then a highlight pass over the bold, then a short summary in the reader's own words -- and each layer sits on top of the last rather than replacing it. Three things from this validate daat's existing design without requiring any change: distillation should be "just in time" (triggered by actual reuse, not run eagerly over the whole pool -- `knowledge.maybe_distill`'s retrieval-gated trigger already works this way), it should be additive rather than destructive (`knowledge.distill` creates a new document linked via `source_document_id`; the source is never edited or replaced), and only the highest-value fraction survives each pass (`DISTILL_SYSTEM_PROMPT`'s "extract the single core idea... remove anything not essential" is already this principle). The one thing this pass *did* take directly from Progressive Summarization: Layer 0 is Layer 0 regardless of its own length or how well-formatted it already looks -- a raw source doesn't earn maturity credit for its own shape, only a deliberate editorial pass does. That is the exact fix Tier 2's definition needed (see below). A second idea from the same method -- staged intermediate layers (an explicit "excerpted" state between raw import and full distillation) instead of a single-shot jump straight to Atomic Record -- was considered and deliberately **not** built: it's a real structural addition, not a prompt change, and cuts against daat's own "keep the core minimal" design philosophy. The risk that motivated considering it (a single-shot distillation losing nuance the source actually asserted) is instead mitigated by teaching the existing bidirectional tier-recompute to check fidelity against the source and demote when it's lost something -- see "Fidelity-to-source demotion" below.

**[Diátaxis](https://diataxis.fr/)** (tutorials / how-to guides / reference / explanation) splits documentation by *purpose*, not maturity -- a genuinely different axis from anything daat's tier ladder tracks. It's flagged here as a real, considered idea for the future (tagging a document as "this is a protocol" vs. "this is a finding," independent of how far along it is), not something built now: it would be a second orthogonal categorization system layered on top of the existing one, and daat's stated design preference is a minimal, domain-agnostic core (see `architecture.md`'s "No domain vocabulary in core") rather than adding axes speculatively.

**[The DIKW pyramid](https://journals.sagepub.com/doi/10.1177/0165551508094050)** (data -> information -> knowledge -> wisdom) was checked and explicitly rejected as a model to borrow from. It's the best-known tiered knowledge model in the information-science literature, but Frické's widely-cited critique ("The Knowledge Pyramid: A Critique of the DIKW Hierarchy") identifies a real logical error in how the levels are claimed to relate to each other, and it predates -- and has no real answer for -- the misinformation/disinformation problems an AI-assisted retrieval system like daat has to actually contend with.

**Verdict:** the four-tier ladder stays. It's already well-aligned with the most battle-tested lightweight personal-knowledge-management model (Zettelkasten) plus a reference-article tier that Wikipedia's own scale validates as a real, distinct thing worth having. The actual gap this research pass closed was definitional precision *within* the existing tiers, not the tier count or structure.

## Real misclassification patterns found while dogfooding

Prompt wording was checked against real documents in a live deployment's knowledge pool (via read-only DB access), not just reasoned about abstractly. Four distinct, concrete failure patterns turned up, each now encoded directly in `TIER_JUDGMENT_SYSTEM_PROMPT`/`DISTILL_SYSTEM_PROMPT` (see the "found live" comments immediately above each prompt in `knowledge.lua` for the code-level detail). Deployment-specific content -- names, titles, exact wording -- is deliberately left out here; only the general shape of each pattern is worth keeping in the platform's own docs.

- **A reminder judged Atomic Record.** A distilled note whose entire content was an instruction -- who must do some specific task, by when -- got judged Tier 3. It was short, single-topic, plain prose, so it slipped past the prompt's original bar (which only ever excluded raw data tables and bare link lists). A reminder states what someone should *do*; a definition states what something *is* -- distinct things, and only the second belongs at Tier 3.

- **Subject-title-shaped candidates, not hypotheses or definitions.** Surfaced directly in a real curation conversation: asked to propose Atomic Record candidates from a cluster of related documents, the agent's first draft came back as topic labels -- accurate names for what the cluster was about ("X vs. Y considerations," "Z parameters for \<subject\>"), asserting nothing themselves. The human reviewer's correction was direct: *"I prefer the atomic record to be more like hypothesis or definition and not a subject title."* Encoded as its own excluded case, distinct from both the reminder case and the raw-data/link-list case: a title doesn't even claim to be an instruction or a fact, it just names an area.

- **Duplicate distillation across a context-compaction boundary.** In that same conversation, the agent distilled the same underlying idea from the same source document twice, because a context compaction between turns erased its memory of already having done it once. The reviewer had to explicitly ask for the duplicate to be archived. Fixed by adding a before-you-distill duplicate check to the two tool-using surfaces that can actually act on it (the `knowledge.distill` tool description, and `KNOWLEDGE_DISTILL_SYSTEM_PROMPT`) -- not to `DISTILL_SYSTEM_PROMPT`, which runs as a single-shot call with no search tool available to check anything with.

- **Verbatim source-document imports judged Developed Reference, inconsistently.** Sampling real Tier 1 and Tier 2 documents turned up several verbatim, untouched imports of full external source documents -- author/abstract/keywords-style front matter, even leftover text-extraction artifacts still sitting in the body -- classified Tier 2. Other imports of the exact same kind, equally untouched, sat at Tier 1 instead: an arbitrary split driven by nothing but how long or multi-section the original document happened to be, the same "shape alone isn't the bar" failure already fixed once for Tier 3, one level down. Contrast: a real write-up actually authored on the platform (a synthesized summary with its own structure -- objective, method, findings) correctly earns Tier 2, because someone genuinely organized it as a reference. Tier 1 and Tier 2's definitions were both rewritten to require genuine editorial work by someone on the platform, not just length or a multi-section shape; a raw import is capped at Curated Draft regardless of size until it's actually reworked.

## Fidelity-to-source demotion

A document's tier was already recomputed bidirectionally on every review (task #87) -- if a document's *own* current content degrades or changes shape, it drops back down, not just up. What it never did is compare a distillation against the source it was distilled from, so there was no way to catch a distillation that reads as a clean, well-shaped Atomic Record in isolation but actually dropped, overgeneralized, or misstated a qualifier or exception the source clearly asserted. This is the concrete, mechanism-level answer to the single-shot-distillation risk Progressive Summarization's staged layers are designed to avoid (see above): rather than adding a staged pre-distillation pipeline, `knowledge.judge_promotion_target` now fetches the source document's content too, whenever the document under review has `source_type == "distilled"` and a `source_id`, and feeds both to the model side by side (source truncated to `TIER_JUDGMENT_SOURCE_MAX_CHARS`, 20000 characters, so a review of a note distilled from a 200KB+ paper import doesn't feed the whole paper into a routine judgment call every time). `TIER_JUDGMENT_SYSTEM_PROMPT` now instructs the model to check fidelity, not just shape, when a source is shown: a distillation that misrepresents its source stays Curated Draft until it's fixed, however definition-shaped it reads on its own.

## Known limitation, left as-is by explicit decision

A freshly created distilled document sits at Tier 0 until it's actually retrieved enough times to become `due_for_review` (`retrieval_count >= 2` or `effective_heat >= 1.15`) -- confirmed directly against a live deployment: every document distilled during the same curation session referenced above had zero rows in `knowledge_tier_review`, meaning the tier-judgment model had never even been asked about any of them. For a low-traffic note nobody happens to search for, this can mean it never gets its first real tier assessment at all. This is deliberate, tested behavior, not an oversight -- `tst/integration/knowledge_context.bats` explicitly asserts a document's tier stays `0` immediately after distillation completes -- and fixing it (e.g. judging tier immediately on distill, or lowering the review threshold) is a real design/behavior change, not a prompt tweak. Raised and explicitly left alone per platform-owner decision; noted here so it isn't rediscovered as a surprise later.
