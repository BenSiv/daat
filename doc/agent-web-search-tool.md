# Agent tool: internet search, approved per call

## Phase 1 -- implemented (DONE)

The chat agent can search the public internet, with every individual call requiring explicit human approval before it runs -- each search query is a real data exit from this system (the query text, and anything embedded in it, e.g. context pulled from a document the agent is working on) -- and every result carries an exact citation/link back to its source.

**Update (search-provider migration):** `src/web_search.lua` -- the single hardcoded module this section originally described -- has since been split into a facade + swappable backend, matching `agent_provider.lua`'s own pattern (see doc/architecture.md's "Providers" section): `src/search_provider.lua` (facade -- `search`/`format_results`, backend picked by `platform.lua`'s `search_provider` field, default `"google_cse"`), `src/provider/search_google_cse.lua` (today's real backend, moved as-is), `src/provider/search_test.lua` (the `WEB_SEARCH_TEST_RESULTS`-scripted stub, previously an env-var branch inside `web_search.search` itself, now a real selectable provider the same way `agent_provider`'s own `"test"` backend is). Every filename below reflects the *original* Phase 1 shape; read them as historical.

**The approval mechanism needed no new infrastructure**, as anticipated: `AGENT_TOOLS.internet_search.search` (`src/agent.lua:1080-1090`-ish, alongside the other tool groups) is marked `destructive = true`, and the existing pending-approval flow every other destructive tool already goes through (`agent_pending_action` / `agent.run_turn`'s destructive-detection branch / `agent.approve_pending`/`deny_pending` / `POST /api/chat-widget-approve`/`-deny`) picked it up with zero changes -- confirmed by `agent_provider_claude.lua:30-37`'s own pre-existing comment, which named this exact tool and this exact requirement before it was built: a provider-native search tool (Claude's server-executed `web_search`) was rejected specifically because it can't be gated this way.

**Search backend: Google Programmable Search (Custom Search JSON API).** New module `src/web_search.lua` mirrors `agent_provider_claude.lua`'s `claude_post` shape closely: reads `GOOGLE_SEARCH_API_KEY`/`GOOGLE_SEARCH_ENGINE_ID` via `os.getenv` (never through `config.platform_config()`, which is for non-secret tunables only), `shell_quote`s every value, issues a GET via `curl -s -G --data-urlencode` (CSE is GET-based, unlike the LLM providers' POST-with-temp-file), and follows the same four-stage error handling every provider call here uses: missing credentials -> no response -> bad JSON -> API-level error.

**Citations are structural, not just instructed.** `web_search.format_results` mirrors `document.search`'s own dispatch-branch convention (`src/agent.lua`): a plain-text block, one result per entry as a `<title> (<url>)` header followed by its snippet, blank-line-separated -- putting the URL directly in each result's own header, not buried in a JSON blob, makes citing the source the path of least resistance. Reinforced in two places, since this was a hard requirement: the tool's own `description` explicitly instructs citing the source URL, and a short paragraph was added to `agent.default_system_prompt` (this codebase had zero citation/link guidance anywhere before this, and no tool-specific system-prompt hook to attach one to instead -- it's a direct addition to that static string).

**Test-mode gate, the first of its kind for a tool's own backend.** `WEB_SEARCH_TEST_RESULTS` (checked inside `web_search.search`, mirrors `agent_provider_test.lua`'s `AGENT_TEST_RESPONSES` gate exactly in shape) lets bats integration tests exercise the full path -- scripted model call -> pending_approval -> approve -> real `execute_tool` dispatch -> canned results -> citation-formatted `tool_result` -- with no real network call and no real credentials in CI. Confirmed before building this that `internet_search.search` is the *first* tool needing its own external side effect faked this way; `document.search` never needed it, since it's already local/deterministic against the test SQLite store.

**No capability gate beyond ordinary chat access.** Unlike `document.create`'s `agent.check_write_capability`, this tool has none -- the pending-approval flow's only authorization is session ownership (a user can only approve/deny their *own* pending actions), not a capability check, so any authenticated user who can already chat can already use this, same as every other non-admin-gated tool.

**Result count is fixed server-side (5), not a model-controlled parameter** -- matches `document.search`'s own fixed `5`, and there was no real reason found to expose it as a knob yet.

**Not resolved here -- infra, blocked on external provisioning:**
- **GCP Secret Manager wiring** (`/root/software/infra/gcp/lims/`) for `GOOGLE_SEARCH_API_KEY`/`GOOGLE_SEARCH_ENGINE_ID`, mirroring the exact existing `PLATFORM_MARIADB_PASSWORD`/Benchling-credentials pattern (Terraform secret + IAM grant, a `gcloud secrets versions access` fetch in the instance startup script, a new line in the `/run/secrets/platform.env` heredoc docker-compose's `env_file:` already loads) -- mechanical to add, not yet applied.
- **Blocked on the user provisioning both credentials first**: enabling "Custom Search API" + generating an API key in the `celleste-elab` GCP project, and creating a Programmable Search Engine at programmablesearchengine.google.com (a separate product, no Terraform/gcloud path creates this half) to get the `cx` value. Nothing here can create either.
- **Prompt-injection surface from web content reaching the model's own context** is mitigated somewhat by using the search API's own short snippets rather than fetching/parsing full page HTML, but not fully resolved -- noted as a real, still-open risk, not a solved problem.

**Verified:** `tst/unit/web_search.lua` (pure `format_results` tests -- citation formatting, blank-line separation, missing-snippet/empty/nil-response handling, no network) and `tst/integration/web_search.bats` (destructive-pause, approve-with-fake-results-cites-URL, deny-never-calls-backend, and a real credentials-missing error path -- all via `WEB_SEARCH_TEST_RESULTS`, no live API key needed) pass alongside the full existing suite.
