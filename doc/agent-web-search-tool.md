# Agent tool: internet search, approved per call

## Phase 1 -- open, not yet scoped

The idea: give the chat agent a web/internet search tool, with every individual call requiring explicit human approval before it runs -- each search query is a real data exit from this system (the query text, and anything embedded in it, e.g. context pulled from a document the agent is working on), not something that should fire silently.

**The approval mechanism this needs already exists, in full, today.** Tools are declared in `AGENT_TOOLS` (`src/agent.lua:725`, e.g. `document.search` at `:727-735`) with a `destructive` flag. `agent.run_turn` (`src/agent.lua:2362`) already detects any `destructive = true` call, persists it as a pending `agent_pending_action` row instead of running it (`:75`, `:2544`), and returns a `pending_approval` status; a separate request resumes it via `agent.approve_pending`/`agent.deny_pending` (`:2596`, `:2626`), wired to `POST /api/chat-widget-approve`/`-deny` (`src/cgi.lua:1495-1550`). The chat widget UI already renders an Approve/Deny prompt and blocks further input while one is pending (`src/html.lua:5171-5180`). Marking a new `internet_search` tool `destructive = true` gets "approve every single call, no exceptions" for free -- this isn't new infrastructure to build, it's the existing gate every other destructive tool (document create/update, etc.) already goes through.

**Already anticipated, not just discovered here:** `agent_provider_claude.lua:30-37`'s own comment states that a future web-search capability "belongs in AGENT_TOOLS as an ordinary custom tool ... going through that same approval gate -- not as one of Claude's server tools," explicitly rejecting Claude's built-in server-executed `web_search` (which would run inside Anthropic's own infrastructure, invisible to and unable to go through this app's local pending-approval flow). Any implementation needs to honor that constraint -- a provider-native search tool is the wrong shape for this feature regardless of how much simpler it'd be to wire up, since it can't be gated.

**Not resolved here, worth deciding before implementing:**
- **Which search backend.** No existing search API integration anywhere in this codebase to build on -- something has to be chosen and, presumably, paid for/licensed (a Search API of some kind; there is no free unlimited option worth relying on).
- **How the outbound request itself gets made.** No egress control or generic outbound-HTTP primitive exists in this codebase today -- the two LLM providers each reach their API via a hardcoded `curl` shell-out (`agent_provider_claude.lua:48,81`, `agent_provider_vertex.lua:97,126`), not a shared HTTP client. This would be the first tool making genuinely arbitrary outbound requests (URL/query determined by the LLM, not hardcoded) -- worth deciding whether that's a `curl` shell-out matching the existing provider pattern, or something using `socket.lua`/`ssl.lua` (already bundled, per `bld/build.sh`'s file list) directly.
- **What the approval prompt actually shows.** For informed consent on a real data exit, the human approving needs to see the literal query text (and, ideally, which document/context it was derived from) before approving -- not just "internet_search wants to run." Whatever the pending-action UI shows for other destructive tools today should be checked against this bar specifically.
- **Whether/how search results get sanitized before returning to the model.** A web page's content is untrusted input reaching the agent's context -- this doc doesn't scope a prompt-injection mitigation, but whoever implements this should treat search results the same way this codebase already treats untrusted external text elsewhere (verified: no existing precedent for consuming raw external content was found; this would be a new trust boundary).
