# Entity relation diagram: draggable/rearrangeable boxes

## Phase 1 -- open, not yet scoped

`html.render_relation_diagram` (`src/html.lua:2232-2385`, backing `GET /data`, `src/cgi.lua:787-799`) renders `schema.relationships()`'s entity-type graph as an inline SVG ERD: each entity type is a box listing its real fields, edges connect the specific referencing field's row to the target type's `id` row with cardinality labels. Layout is a deterministic, server-computed "shortest-column-first" packing (`src/html.lua:2260-2284`) -- explicitly *not* a physics simulation (the function's own comment says so). Box positions are fixed once rendered; the only client-side interactivity today is hover/click highlighting and a list/diagram toggle (`html.diagram_js`, `src/html.lua:2411+`) -- no drag, no rearrangement.

The idea: let a user drag boxes to their own preferred arrangement, the same way `/knowledge-graph`'s document nodes now work (`doc/knowledge-graph-explorer.md` Phase 3) -- worth doing now that that page proved out the pattern (camera-independent world coordinates, drag-to-reposition, per-browser `localStorage` position caching so a rearrangement survives a reload) and worked through real bugs (an energy-sleep threshold that has to be normalized by node count, not a raw sum, or it can run indefinitely on a large graph; per-frame velocity clamping so repulsion spikes don't read as jitter).

**Not resolved here, worth deciding before implementing:**
- **SVG-native drag vs. switching to canvas.** `/knowledge-graph` is canvas because it has no DOM element per node to hook into and needs custom hit-testing for pan/zoom/hover. This diagram already has a real `<rect>`/`<g>` per box, so plain pointer-event dragging on the existing SVG elements (updating a `transform="translate(...)"`) may be simpler here and wouldn't require duplicating the canvas approach at all -- entity-type count is also typically far smaller than a document pool's node count, so the case for a live physics simulation (vs. just letting a user drag boxes to fixed spots, no simulation at all) is weaker than it was for the knowledge graph.
- **Whether physics is wanted at all**, or just plain drag-to-reposition. The knowledge graph's force simulation exists because *nobody* has a natural starting layout for an arbitrary document pool. The relation diagram already has one (the packed-grid layout) -- a live simulation would need a reason beyond "we now know how to build one."
- **Edge redrawing.** Edges here connect specific field *rows*, not box centers -- dragging a box needs its outgoing/incoming edges to follow the right row's position, not just re-anchor to a box centroid.
