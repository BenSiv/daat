# Entity relation diagram: draggable/rearrangeable boxes

## Phase 1 -- drag-to-reposition (DONE)

`html.render_relation_diagram` (`src/html.lua:2232-2385`, backing `GET /data`, `src/cgi.lua:787-799`) renders `schema.relationships()`'s entity-type graph as an inline SVG ERD: each entity type is a box listing its real fields, edges connect the specific referencing field's row to the target type's `id` row with cardinality labels. Layout is still a deterministic, server-computed "shortest-column-first" packing (`src/html.lua:2260-2284`) -- the three open questions below resolved against plain drag, no physics.

Resolved, and why:
- **SVG-native drag, not canvas.** Each box is a real `<g class="platform-diagram-node">`; dragging just updates its own `transform="translate(dx,dy)"` and its children (rect, field rows) move for free. No hit-testing code needed at all -- the browser's own DOM event targeting does it.
- **No physics on load.** The packed-grid layout is already a sane starting point (unlike the knowledge graph's arbitrary document pool), so a fresh page load is still plain, instant, deterministic placement -- physics is opt-in (Phase 2, below), never runs automatically.
- **Edges follow their anchored row, not a box centroid.** Each edge's original `x1/y1/x2/y2` (and its two cardinality-label positions) are captured once at load (`edge._platformOrig`) and re-derived every drag frame as `original + the relevant endpoint box's current offset` -- so a line anchored to one specific field row tracks that row's box precisely, even when the *other* end's box has also been dragged independently.

Same `localStorage` persistence convention as `/knowledge-graph` (`platform-relation-diagram-layout-v1`, a browser-local `{type: {dx, dy}}` map, restored on load and saved on drag-release) -- per-viewer only, never shared/synced, degrades silently to "no cache" under private browsing or a disabled store. Click-to-browse (mouse-down-and-up with no movement in between) and the existing hover-to-highlight-relations behavior are both unchanged -- drag only kicks in once the pointer actually moves past a small threshold, same distinguishing mechanism `/knowledge-graph`'s click-vs-drag uses.

## Phase 2 -- auto-arrange (DONE, rewritten twice)

An "Auto-arrange" button next to the hint text runs a force-directed pass on request -- shortens edges and, as an emergent property of spreading connected clusters apart, tends to reduce crossings. Not a guaranteed crossing-minimizer (that's a much harder graph-theoretic problem).

**Current implementation: Fruchterman-Reingold** (Fruchterman & Reingold, "Graph Drawing by Force-directed Placement", 1991) -- the standard, published algorithm for this job, not an ad-hoc force mix. Repulsion (`k*k/d`) between *every* pair of boxes, attraction (`d*d/k`) along edges, and per-node displacement capped by a "temperature" that cools linearly over a fixed 300 iterations -- convergence is guaranteed by the schedule itself, not by hoping the forces happen to settle. `k` (ideal distance) isn't one global constant: `idealDistance(a, b)` floors the classic `sqrt(area/n)` value at the two boxes' own combined half-diagonals plus a gap, so equilibrium never asks two boxes to sit closer than their actual footprints allow. A short 40-iteration AABB-overlap cleanup pass runs afterward, since point-based FR doesn't know a box's real footprint beyond that floor (the floor is a worst-case diagonal distance; two boxes settling axis-aligned at exactly that distance can still clip).

Two real bugs found and fixed getting here, both worth recording since they're easy to reintroduce:

1. **First version: everything collapsed to the middle, no repelling.** Separation was AABB-overlap-based -- it only pushed two boxes apart once their margins already overlapped. Any pair that wasn't already touching felt *zero* separating force, so the constant center-pull (nothing opposed it for most pairs) dragged the whole layout inward over many iterations. Fixed by switching to genuine long-range repulsion (FR's `k*k/d`) that acts between every pair regardless of distance, same as `/knowledge-graph`'s point repulsion -- the AABB pass is now a supplementary cleanup, not the only thing keeping boxes apart.
2. **Second version (the original ad-hoc spring+AABB design, before switching to FR): boxes jittering, stuck against each other.** The spring rest length was one flat constant (260px), shorter than the actual footprint of any reasonably tall box (many fields = a tall, sometimes 300px+, rectangle at a fixed 200px width) -- so for those pairs, the spring pulled two boxes toward a distance the AABB separation immediately rejected as overlapping, every frame, forever. This is what motivated `idealDistance`'s box-aware floor, carried forward into the FR rewrite rather than just patched in place.

Same `localStorage` persistence as Phase 1 -- the result is saved to the same cache and survives reload, indistinguishable from a manual arrangement to anything that reads it back.

**Verified:** full suite (`./bld/test.sh`) stayed green -- no new automated coverage (same bats limitation as Phase 1 and the knowledge graph); manual check covers auto-arrange on a real schema (edges visibly shorten, boxes spread out and separate without overlap, no collapse-to-center, no jitter/sticking), and that dragging still works normally afterward.

## Phase 3 -- pan, zoom, wider viewport (DONE)

The diagram's own container width was capped at 800px (`platform_container_css(800)`, shared with this page's plain entity-type list view) -- far too narrow for a multi-column packed-grid ERD, forcing native scrollbars to see the whole thing. Widened to 1400px for this page specifically (the list view just reflows into more columns at that width, harmless).

Pan and zoom are native SVG `viewBox` manipulation, not a group transform (unlike the knowledge graph's canvas, which has no equivalent to `viewBox` and has to fake a camera by hand) -- scroll to zoom, cursor-anchored so the point under the pointer stays fixed as the `viewBox`'s width/height shrink or grow (clamped to 0.15x-4x the diagram's natural size); dragging the SVG's own background (not a box -- `mousedown`'s target is checked against `.closest('.platform-diagram-node')` first, so this never fights the existing per-box drag) pans by shifting `viewBox`'s x/y. A "Reset view" button snaps back to the diagram's original `viewBox`, captured once at render time in `data-natural-view`. Existing per-box drag needed no changes at all -- `getScreenCTM()` (already used to convert mouse coordinates to SVG user-space) reflects whatever the current `viewBox` is automatically.

The SVG element itself dropped its fixed `width`/`height` attributes in favor of CSS (`width: 100%; height: 70vh`) so it fills the available (now much wider) container responsively, with `viewBox` continuing to define the coordinate system independent of however large the element is actually rendered.
