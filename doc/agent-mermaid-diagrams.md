# Agent tool: Mermaid diagram creation and rendering

## Phase 1 -- open, not yet scoped

The idea: let the chat agent produce diagrams (flowcharts, ER diagrams, sequence diagrams, etc.) using Mermaid syntax, rendered as real diagrams rather than dumped as code text.

**Nothing to build on today.** No Mermaid (or any diagram-rendering) library exists anywhere in this codebase -- `vnd/` (the vendored third-party asset directory, `config.vendor_assets_dir()`, `src/config.lua:196-209`) holds only `toastui` (the document editor) and `browserprint`. `mermaid` only appears inside a couple of *this repo's own docs* as fenced blocks (`doc/document-link-flow.md`, `doc/link-strength-redesign.md`) -- rendered by GitHub when those files are viewed there, nothing this app itself does.

**Where rendering should happen -- client-side, vendored, not server-side.** Two real options exist:
- **Client-side (recommended):** vendor `mermaid.js` the same way Toast UI Editor is already vendored -- a real third-party library checked into `vnd/`, served via the existing `/vendor?name=X` allowlisted route (`src/cgi.lua:569-587`), rendering `<pre class="mermaid">`-tagged blocks into SVG in the browser. This is the same pattern every other Mermaid-consuming tool (GitHub, GitLab, Obsidian) uses, and fits this codebase's own vendoring convention exactly -- unlike the knowledge graph/relation diagram's force layouts (deliberately hand-rolled specifically to avoid a dependency for a small, self-contained problem), a full diagram-syntax parser and layout engine is genuinely hard to reimplement and not the kind of thing "minimal dependencies" (`doc/why-luam.md`) argues against vendoring.
- **Server-side (rejected):** rendering Mermaid to a static SVG/PNG server-side needs Node.js (`mmdc`, Mermaid's own CLI) or a headless browser -- infrastructure this Lua/C-based platform has none of today, and adding either would be a far heavier change than vendoring one JS file. Not worth scoping further unless client-side rendering turns out to be infeasible for some reason not yet identified.

**Where a diagram actually reaches the reader -- two surfaces, one underlying gap.** Markdown rendering shells out to `cmark-gfm` (`document.render_markdown`, `src/document.lua:749-761`, extensions: `table`/`strikethrough`/`autolink` only, `--unsafe` raw-HTML deliberately off) with no fenced-code-block extension point today -- a ```` ```mermaid ```` block currently renders as inert `<pre><code class="language-mermaid">` text, both in documents and in chat (chat's `assistant`/`self_check`/`compaction_summary` roles are the only ones run through markdown at all, `html.CHAT_MARKDOWN_ROLES`, `src/html.lua:4941`; every other role, including `tool_result`, is escaped as plain text, `src/html.lua:5156-5157`). Whatever the fix is, it likely wants to live in *one* shared place both surfaces already go through, rather than two separate implementations -- worth checking whether documents and chat actually share the same `render_markdown` call or diverge before assuming a single fix covers both.

**Possibly not a new AGENT_TOOLS entry at all.** The agent can already create/update documents (`document.create`/`document.update`, referenced in `AGENT_TOOLS`) and already produces markdown-rendered `assistant` chat messages -- if fenced-mermaid-block handling is added to the shared rendering path above, the agent may not need a *dedicated* diagram tool to "create" one; it could just write a ```` ```mermaid ```` fence via the tools it already has, in a document or directly in a chat reply, and have it render. A dedicated tool would mainly buy discoverability (the model reliably reaching for it when a diagram is the right answer) rather than new capability -- worth deciding deliberately rather than defaulting to "add a tool" before checking whether the existing ones already cover it once rendering works.
